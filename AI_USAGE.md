# AI Usage Report — TicketManager

## AI TOOL USED

Cursor (AI-assisted coding in the IDE), including multi-step implementation prompts for authentication, role dashboards, and SLA handling.

## WHAT I ASKED AI TO DO

- Implement authentication (HTTP-only JWT cookie) and light/dark theme.
- Build Student, Staff, Department Admin, and System Admin workflows incrementally.
- Add SLA breach detection, global analytics, and audit logging.
- Perform a final integration/cleanup pass without rebuilding the application.

## PROMPTS THAT WERE USEFUL

- Vertical-slice prompts per role (Student → Staff → Department Admin → Admin) with explicit “do not rewrite auth” constraints.
- Backend-first rules (authorization on server, SLA owned by backend, no student priority selection).
- Final cleanup prompt with business-flow checklist and “no npm / no claiming tests” instruction.

## CODE GENERATED BY AI

- Most of `client/src/` UI (dashboards, modals, contexts, services).
- Most of `server/` ticket/auth/analytics controllers, routes, SLA breach service, and Mongoose models.
- Project documentation drafts (`READ_ME.md`, `README.md`, this file).

## CODE MODIFIED

- Existing `server/index.js`, routing, and middleware wiring as features were added.
- Shared components (`StaffTicketDetailModal`, `SlaDisplay`, `AppShell`) extended per role rather than duplicated.
- Priority/authorization guards adjusted when role boundaries were clarified (e.g. status changes limited to Staff).

## AI OUTPUT THAT WAS WRONG

1. **Student ticket detail access (403)** — `GET /api/tickets/:id` failed for students after `studentId` was populated; ownership check compared an object to a string.
2. **Demo account emails in docs** — README listed `finance.*@TicketManager.com` while MongoDB seed used `staff@ticketmanager.com` and `accounts.admin@ticketmanager.com`.
3. **Staff resuming pending tickets** — Initial staff status transitions allowed `PENDING_STUDENT_ACTION → IN_PROGRESS`, bypassing the student response step.

## HOW THE PROBLEM WAS IDENTIFIED

- API validation with login cookies showed 403 on student ticket detail.
- Listing users in MongoDB during development showed actual seeded emails.
- Business-flow review in the final cleanup pass flagged the missing student respond endpoint.

## HOW IT WAS FIXED

- Added `getTicketStudentId()` helper for populated `studentId` in access checks.
- Updated demo account documentation to match seeded users and passwords used in the environment.
- Added `PATCH /api/tickets/:id/respond` for students and removed staff transition from `PENDING_STUDENT_ACTION` to `IN_PROGRESS`.
